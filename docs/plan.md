# 簡易データカタログ 計画（実装済みの内容に合わせて更新）

> この計画は、実装を終えたあとに、その内容に合わせて書き起こしたものです。
> 実装はコミット `3e28f90`（ブランチ `feature/simple-datacatalog`）の時点のものです。
> 使い方は README を、役割と問いの考え方は `docs/question-driven.md` を参照してください。

---

## 1. 目的

手元のデータファイルを登録し、次のことができる小さなデータカタログを作る。

- データの意味（説明・タグ・プロパティ）を残し、探せるようにする
- データ同士のつながり（リネージ）を残す
- 誰が責任を持ち、誰が守るのか（データオーナー／データスチュワード）を残す
- **データは問いに答えるために存在する** という考え方で、データがどの問いに使われているかを残す

運用の目安は、1台のサーバーを数人〜数十人で使う規模とする。

## 2. 設計の方針

| 方針 | 内容 |
|---|---|
| 小さく作る | Python + Streamlit + SQLite の1プロセスで動かす。ほかのサーバーは使わない |
| 入力した情報を失わない | データを更新しても、説明・タグ・プロパティ・役割・リネージ・問いを引き継ぐ。スキーマを更新するときも、できるだけデータを残す |
| 止めずに促す | 必須項目や問いの記入はエラーにせず、充実度や「💡 次に書くとよいこと」で気づかせる |
| 項目単位のあと勝ち | 同時に編集しても、別々の項目の変更は両方残る。同じ項目を同時に変えたときだけ後勝ちとし、上書きされた値は変更履歴で追える |
| 役割は機能で分ける | オーナーは役職で、スチュワードは人で持つ。割り当ては1行1件で持ち、3層への拡張に備える（docs §7） |
| 表記ゆれを防ぐ | 自由入力の欄（組織・担当者・テキスト型のプロパティなど）には、過去の入力値を候補として出す |

## 4. データモデル（SQLite、スキーマ v4）

| テーブル | 内容 |
|---|---|
| `domains` | ドメイン（オーナーを設定する基本の単位） |
| `assets` | アセット（ファイル）。`domain_id` で所属ドメインを持つ |
| `columns` | カラム（名前・型・並び順・説明） |
| `tags` / `asset_tags` / `column_tags` | タグ（使われなくなったら自動で消す） |
| `lineage` | 上流 → 下流の辺（自己参照を禁止。循環はアプリ側でチェックする） |
| `property_definitions` / `asset_properties` | プロパティの定義（標準＋カスタム）と、アセットごとの値 |
| `users` | ユーザー（ロール、有効／無効、パスワードハッシュ、メールアドレス、説明） |
| `change_log` | 変更履歴（アセット名・ユーザー名はその時点の値を文字列で持つ） |
| `role_types` | 役割の種類（オーナー、スチュワード（業務）、スチュワード（技術））。データとして持つ |
| `role_assignments` | 役割割り当て（1行1割り当て。対象はドメインかアセットのどちらか一方） |
| `questions` / `question_assets` | 問いと、問いに使うアセット（多対多） |

**版管理と移行**（`PRAGMA user_version`）
- 版を上げるときに、列やテーブルを足すだけで済む場合（v2→v3、v3→v4）は、データを残したままその場で上げる。列の追加は、列がすでにあれば何もしない（何度実行してもよい）。
- それより古い版の DB は `catalog.db.bak-日時` に退避して、空の DB で作り直す。

## 5. 機能

### 5.1 登録とデータ更新
- 対応形式は CSV / Parquet / JSON / JSONL。ファイルのアップロードか、ローカルのパス（ファイルまたはディレクトリ）を指定して登録する。
- カラム名と型を自動で取り込み、行数を数え、先頭20行をプレビューできる。
- **データ更新**：詳細ページで「元ファイルから再取込」または「ファイルを差し替え」を行う。同じアセット名で登録し直した場合も更新になる。
  - アセットの ID は変わらない。そのため説明・タグ・プロパティ・役割・リネージ・問いはすべて残る。
  - 名前が変わったカラムは、画面で対応付けると説明・タグを引き継ぐ。大文字小文字や `_` だけの違いは、自動で候補にする。
  - なくなったカラムは、確認を取ってから削除する。

### 5.2 説明・タグ・プロパティ・充実度
- アセットとカラムに、説明とタグを付けられる。
- **標準プロパティ**：ソースシステム・更新頻度・公開範囲・機密区分・保持期間（以上は必須）と、利用上の注意（任意）。削除と型の変更はできないが、名前・選択肢・必須かどうかは変えられる。
- **カスタムプロパティ**：管理者が定義する。型はテキスト・長文・数値・日付・選択肢・URL から選ぶ。
- **充実度**：説明・必須プロパティ・オーナー（4つの責任範囲すべてが誰かに割り当てられていること）・スチュワード（1人以上）のうち、入力済みの数。未入力でも保存はできる。

### 5.3 リネージ
- 直接の上流と下流を登録する。循環になる関係は登録できない。
- 中心にするアセットと、たどる深さ（1〜5）を選んでグラフで表示する。各ノードには、そのデータが答えている問いの数を添える。

### 5.4 役割（データオーナー／データスチュワード）
- **オーナー**：役職で持つ。項目は組織、役職、担当者、責任の範囲（問いの受諾／定義／品質基準／アクセス承認）、委譲規程、最終確認日。
- **スチュワード**：業務と技術の2種類。人で持つ。項目は組織、担当者、担当の範囲、問い合わせ窓口、エスカレーション先、最終確認日。
- **継承**：アセットは所属ドメインの割り当てを継承する。継承元は保存せず、表示のたびに計算する。
  - オーナーは **責任範囲ごと** に上書きする（例：経理部長が「定義」だけを受け持つと、残りの範囲は営業部長から継承する）。
  - スチュワードは **種類ごと** に上書きする。
- **棚卸し**：最終確認から183日を過ぎた割り当てを「要確認」にする。棚卸しページで、組織や役職・担当者で絞り込み、まとめて「確認済み」にできる。

### 5.5 問い
- **一文から始める**：必須なのは問いの文だけ。番号は Q-001 形式で自動で振る。
- **あとから育てる**：種別、持ち込んだ部門、依頼者、必要な品質、受諾状態（申請中／受諾／条件付き受諾／却下）、受諾者、受諾日、条件、監視担当、品質指標、見直し日、状態（有効／廃止）を、あとから足していける。
- **💡 ヒント**：疑問文になっていない、データが未特定、必要な品質が未記入、受諾者や監視担当や条件や見直し日が未記入、見直し日を過ぎた、といった状態を知らせる（止めはしない）。
- **候補の提示**：
  - 似た問い（重複を避けるため）
  - 使えそうなデータ（文字の2文字組の重なりで探す。形態素解析は使わない）
  - 受諾者は「問いの受諾」を受け持つオーナー、監視担当はスチュワード
  - 受諾にすると受諾日を自動で入れる。見直し日は「半年後」をボタン1つで入れられる
- **ふだんの動線に置く**：
  - **アセット詳細**：答える問いを表示する。0件なら1行で登録を促す。下流を通じて支えている問いも見せる
  - **ホーム**：問いの文でも検索できる。カードに問いの件数を出し、「問い未登録」で絞り込める（維持をやめる候補）
  - **そのほか**：登録の直後の案内、リネージの問い数、棚卸しの見直し期限
- 「問い未登録」は充実度には含めず、別の目印として扱う。

### 5.6 一覧・検索
- キーワードで検索する。対象は名前、説明、カラム、プロパティ値、ドメイン、役割の担当者、問いの文。
- 絞り込み：タグ、ドメイン、選択肢型のプロパティ、未入力の必須項目があるもの、要確認の役割があるもの、問いが未登録のもの。

## 6. ユーザー・権限・履歴

| 操作 | 閲覧者 | 編集者 | パワーユーザー | 管理者 |
|---|---|---|---|---|
| 閲覧（一覧・詳細・リネージ・問い・ドメイン・棚卸し・アセットの変更履歴）、自分のプロフィールとパスワード | ✔ | ✔ | ✔ | ✔ |
| 説明・タグ・プロパティ値・カラム・リネージの編集、問いの登録・編集 | | ✔ | ✔ | ✔ |
| アセットの登録・データ更新・削除、ドメインの付け替え、アセットへの役割割り当て | | | ✔ | ✔ |
| プロパティ定義、ドメインとドメインへの役割割り当て、ユーザー管理、全体の変更履歴 | | | | ✔ |

- **ログイン**：ID とパスワードで行う（scrypt でハッシュ化。パスワードは8文字以上）。初回起動時は、最初の管理者を作る画面を出す。管理者が作ったユーザーは、初回ログイン時にパスワードを変えてもらう。
- **ユーザーの扱い**：削除せず無効化する。最後の管理者を降格・無効化することはできない。メールアドレス（任意・重複不可）と説明（任意）を持つ。
- **権限の確認**：メニューの出し分けに加えて、各ページの先頭と、すべての書き込み関数でも確認する。
- **変更履歴**：すべての書き込みについて、データの変更と同じトランザクションで記録する。アセットの詳細では直近50件、管理者向けのページでは全体を表示する。

## 7. 同時編集と整合性

| 問題 | 対策 |
|---|---|
| 接続を共有すると、トランザクションが混ざる | 接続はページを実行するたびに作り、セッション間で共有しない。WAL モードと `busy_timeout` を使う |
| 読んでから書くまでの間に、他の人の変更が入る | `write_tx` で `BEGIN IMMEDIATE` を使い、差分の計算・循環チェック・最後の管理者チェックを同じトランザクションの中で行う |
| フォームが全項目を書き戻すと、他の人の変更を消してしまう | 開いた時点の値（`FormSnapshot`）と比べて、変えた項目だけを書く。他の人が更新した場合は通知を出し、「最新を読み込む」で更新できるようにする |

## 9. 確認できていないこと・制約

- 候補にない新しい値を自由入力の selectbox（`accept_new_options`）に手入力する操作は、AppTest で再現できない。ブラウザでの確認が必要。
- 問いに使うデータの候補は、文字の2文字組の重なりで測っているため、関係の薄いデータが混じることがある。
- スキーマの移行は、列やテーブルの追加までしか対応していない。列の変更や削除が必要になったら、退避して作り直すことになる。
- ログインの総当たり対策は、失敗したときに1秒待たせるだけ。
