# データカタログ 役割と問いの登録設計（2層版）

## 1. 基本的な考え方

### 1.1 データは問いに答えるために存在する

データカタログでは、データ資産を **「どの問いに答えるためのデータか」** という観点で管理する。

- 問いには **分析上の問い**（例：得意先別の月次粗利はいくらか）と **業務上の問い**（例：この注文は出荷済みか）の両方を含む。
- 品質の基準は抽象的に決めず、**問いに答えるために必要な水準**から導く。
- どの問いにも使われていないデータ資産は、維持をやめる候補とする。

### 1.2 役割は機能で定義し、組織の階層とは切り離す

- 役割は DMBOK と同じく **機能による分類** とし、組織の階層とは別の軸で扱う。
- 組織の階層への対応（部長から課長への委譲など）は、カタログの外の **ドメイン単位の委譲規程** で定める。
- 当面は **オーナーとスチュワードの2層** で運用し、後から中間の層を追加できる構造にしておく。

---

## 2. 役割の定義

| 役割 | 問いとの関係 | 責任 | 主な活動 |
|---|---|---|---|
| **データオーナー** | **問いを引き受け、答えられることに責任を持つ** | 最終的な説明責任。日常の判断は委譲規程に従って委譲できる | 問いの受諾・却下、定義の決定、品質基準の承認、アクセスの承認 |
| **データスチュワード** | **問いに答えられる状態を保つ** | 実行責任 | 品質の監視、原因の調査、修正、メタデータの維持、問い合わせ対応 |

### 2.1 データオーナー

- **問いの受諾**：利用者が持ち込んだ問いに、このデータで答えることを引き受けるかを判断する。
- **定義**：データが何を表し、何を表さないかを決める。
- **品質基準**：受諾した問いに答えるために必要な品質の水準を承認する。
- **アクセス**：誰がデータを使ってよいかを承認する。
- **委譲**：日常の判断（範囲内の是正、優先順位づけなど）は、ドメインの委譲規程に従って委譲できる。委譲しても説明責任はオーナーに残る。

### 2.2 データスチュワード

- **監視**：受諾された問いに対して、必要な品質が保たれているかを日常的に確認する。
- **調査・修正**：品質の問題の原因を突き止め、手順書の範囲内で直す。
- **メタデータの維持**：定義、コード一覧、問い台帳の記載を最新に保つ。
- **窓口**：データの意味や使い方についての問い合わせに答える。
- **エスカレーション**：範囲外の問題は、委譲規程に定めた先に上げる。
- 種別として **業務スチュワード** と **技術スチュワード** を区別する。

### 2.3 データ利用者（役割ではなく関係者）

- 問いを持ち込む主体。
- 問いと必要な品質を問い台帳に登録し、オーナーの受諾を受ける。

## 3. カタログの構造

### 3.1 全体像

```
[ドメイン] ──(オーナーを設定、継承)──▶ [データ資産]
                                          │
                                          ├─(役割割り当て)─▶ オーナー / スチュワード
                                          │
[問い] ──(使うデータ資産)───────────────────┘
  │
  ├─ 受諾者：オーナー
  └─ 監視担当：スチュワード
```

- **ドメイン**：オーナーを設定する基本の単位。データ資産はドメインのオーナーを継承し、例外だけを個別に上書きする。
- **データ資産**：テーブル、データセット、レポートなど。
- **役割割り当て**：データ資産と役割と担当者を1行ずつ結びつける。
- **問い**：データが答えるべき問い。データ資産と多対多で結びつく。

### 3.2 役割割り当ては「1行1割り当て」で持つ

役割を固定の列（オーナー列、スチュワード列）で持たず、1行ずつ登録する。中間の層を追加するときは、役割の種類に値を足すだけで済む。

| データ資産 | 役割の種類 | 担当 |
|---|---|---|
| 受注明細 | オーナー | 営業部長 |
| 受注明細 | スチュワード（業務） | 営業管理課 ○○ |
| 受注明細 | スチュワード（技術） | 情報システム部 ○○ |

## 4. プロパティ定義

### 4.1 役割割り当て（共通）

| プロパティ | 必須 | 内容 |
|---|---|---|
| 対象 | 必須 | ドメインまたはデータ資産 |
| 役割の種類 | 必須 | `オーナー` / `スチュワード（業務）` / `スチュワード（技術）`（将来、`データ管理責任者` を追加できる） |
| 継承元 | 必須 | `ドメインから継承` / `個別設定` |
| 最終確認日 | 必須 | 割り当てが正しいことを最後に確認した日 |

### 4.2 オーナー

| プロパティ | 必須 | 内容 |
|---|---|---|
| 組織 | 必須 | 部門名（例：営業部） |
| 役職 | 必須 | 役職名（例：営業部長）。異動に強いので役職で持つ |
| 担当者 | 任意 | 現在その役職にいる人 |
| 責任の範囲 | 必須 | `問いの受諾` / `定義` / `品質基準` / `アクセス承認` から複数選ぶ |
| 委譲規程 | 任意 | ドメインの委譲規程への参照（3層化への橋渡し） |

### 4.3 スチュワード

| プロパティ | 必須 | 内容 |
|---|---|---|
| 組織 | 必須 | 部門・課（例：営業管理課） |
| 担当者 | 必須 | 実際に窓口になる人。人で持つ |
| 種別 | 必須 | `業務` / `技術` |
| 担当の範囲 | 任意 | 担当する項目のまとまりや作業 |
| 問い合わせ窓口 | 必須 | メールアドレス、チャンネルなど |
| エスカレーション先 | 必須 | 範囲外の問題を上げる先（委譲規程に従う） |

### 4.4 問い（問い台帳）

| プロパティ | 必須 | 内容 |
|---|---|---|
| 問いID | 必須 | 一意の識別子 |
| 問い | 必須 | 疑問文で書く（例：得意先別の月次粗利はいくらか） |
| 種別 | 必須 | `分析` / `業務` |
| 持ち込んだ部門 | 必須 | 問いを持つ部門 |
| 依頼者 | 必須 | 問いを登録した人 |
| 使うデータ資産 | 必須 | 答えるために使うデータ資産（複数可） |
| 必要な品質 | 必須 | 鮮度、粒度、正確性、網羅性などを、問いに即して具体的に書く |
| 受諾状態 | 必須 | `申請中` / `受諾` / `条件付き受諾` / `却下` |
| 受諾者 | 必須 | 受諾を判断したオーナー（データ資産のオーナーと一致させる） |
| 受諾日 | 受諾時に必須 | 受諾した日 |
| 監視担当 | 受諾時に必須 | 品質を監視するスチュワード |
| 品質指標 | 任意 | 監視に使う指標（例：受注入力の遅延件数） |
| 見直し日 | 必須 | 問いがまだ有効かを確認する予定日 |
| 状態 | 必須 | `有効` / `廃止` |

### 4.5 データ資産に追加するプロパティ

| プロパティ | 内容 |
|---|---|
| 答える問い | このデータ資産を使う問いの一覧（問い台帳からの逆参照） |
| 問いの数 | 有効な問いの件数。0件の資産は維持をやめる候補 |

## 5. 運用

### 5.1 問いの受諾の流れ

1. **利用者** が問い台帳に問いを登録する（問い、使うデータ、必要な品質）。
2. **スチュワード** が、現状のデータでその品質を満たせるかを確認する。
3. **オーナー**（または委譲を受けた者）が受諾、条件付き受諾、却下のいずれかを判断する。
   - 品質を満たすために追加の維持負担が出る場合は、利用者と負担について合意する。
4. 受諾した問いには監視担当のスチュワードを割り当て、品質の監視を始める。

### 5.2 定期の棚卸し

| 対象 | 頻度の目安 | 確認すること |
|---|---|---|
| 役割割り当て | 半年ごと、および人事異動の後 | 担当者が正しいか。最終確認日を更新する |
| 問い | 見直し日ごと | 問いがまだ有効か。必要な品質は変わっていないか |
| データ資産 | 年1回 | 有効な問いが0件のものを、維持をやめる候補として洗い出す |

### 5.3 3層に広げる判断の目安

次のような状況が出てきたら、`データ管理責任者` を役割の種類に追加する。

- オーナーによる承認がボトルネックになっている。
- オーナー欄の人が実際には判断していないケースが目立つ。
- スチュワードがエスカレーション先に迷うことが多い。

## 6. 登録例：販売管理データ（営業部）

### 6.1 役割割り当て

| 対象 | 役割の種類 | 組織 | 役職／担当者 | 継承元 |
|---|---|---|---|---|
| ドメイン：販売管理 | オーナー | 営業部 | 営業部長 | 個別設定 |
| 受注明細 | オーナー | 営業部 | 営業部長 | ドメインから継承 |
| 受注明細 | スチュワード（業務） | 営業管理課 | ○○ | 個別設定 |
| 受注明細 | スチュワード（技術） | 情報システム部 | ○○ | 個別設定 |
| 売上実績 | オーナー | 営業部 | 営業部長 | ドメインから継承 |
| 売上実績（計上時点の定義） | オーナー | 経理部 | 経理部長 | 個別設定（会計基準が関わるため上書き） |

### 6.2 問い台帳

| 問いID | 問い | 種別 | 持ち込んだ部門 | 使うデータ資産 | 必要な品質 | 受諾状態 | 受諾者 | 監視担当 |
|---|---|---|---|---|---|---|---|---|
| Q-001 | 得意先別の月次粗利はいくらか | 分析 | 営業部 | 受注明細、単価マスタ、原価 | 明細単位で正確。月末締めの翌3営業日までに確定 | 受諾 | 営業部長 | 営業管理課 ○○ |
| Q-002 | 今月の受注見込はどれくらいか | 分析 | 経営企画部 | 受注明細、見積 | 受注入力が受領から1営業日以内 | 条件付き受諾 | 営業部長 | 営業管理課 ○○ |
| Q-003 | この注文は出荷済みか | 業務 | 物流部 | 受注明細、出荷指示 | 出荷実績がリアルタイムで反映 | 受諾 | 営業部長 | 情報システム部 ○○ |
| Q-004 | 月次決算の売上高はいくらか | 分析 | 経理部 | 売上実績 | 会計上の計上基準に従う。締め日までに確定 | 受諾 | 経理部長 | 営業管理課 ○○ |

※ Q-004 は売上の計上時点の定義を経理部が持つため、受諾者は経理部長になる。

## 7. 設計上のポイント（まとめ）

- **役割は機能で、組織の階層への対応はカタログの外の委譲規程で。**
- **オーナーは役職で、スチュワードは人で持つ。**
- **オーナーはドメイン単位で設定し、継承させる。** 例外だけを個別に上書きする。
- **役割割り当ては1行1割り当てで持ち、3層への拡張に備える。**
- **品質の基準は問いから導く。** 問いのないデータは維持をやめる候補にする。
- **最終確認日と見直し日で、情報が古くならないようにする。**
